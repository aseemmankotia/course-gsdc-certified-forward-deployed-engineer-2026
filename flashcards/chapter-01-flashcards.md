## Chapter 1: The Forward Deployed Engineer Mindset — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | FDE vs Solutions Architect — core distinction? | FDE = embedded with client, hands-on builds/ships working solutions. Solutions Architect = designs system architecture/specs, often pre-sales/advisory, doesn't always implement. Exam tests engagement model + deliverable type, not domain. |
| 2 | FDE vs ML Engineer — core distinction? | FDE owns end-to-end problem: business translation, scoping, deployment. ML Engineer works within a defined scope building/training/optimizing models. FDE often defines the scope the ML Engineer executes within. |
| 3 | FDE vs Consultant — core distinction? | FDE builds and ships working technical solutions embedded at client site. Consultant typically delivers strategic recommendations/frameworks without owning implementation. Exam differentiator: 'builds and ships' vs 'recommends.' |
| 4 | MECE stands for — and tests what? | Mutually Exclusive, Collectively Exhaustive. Mutually Exclusive = no category overlaps another. Collectively Exhaustive = categories cover 100% of the problem space, no gaps. Exam trap: catch-all categories like 'other' or 'general issues' violate mutual exclusivity. |
| 5 | Input-Processing-Output (IPO) model — 3 components? | Input = data/signals feeding the system. Processing = logic/decision/transformation applied. Output = concrete result/decision produced. Vague requirements ('should just work') map to none of these until clarified. |
| 6 | Exam weight for 'FDE Mindset and Problem Structuring' domain? | ~10% of the exam. Lightly weighted numerically but heavily tested conceptually (role distinctions, MECE, IPO appear across scenario questions in other domains too). |
| 7 | Heuristic for separating signal from noise in client requirements? | Signal = specific, measurable, tied to a decision or output (e.g., 'reduce report turnaround from 3 days to 1'). Noise = vague sentiment or symptom language ('it's a mess,' 'should just work'). Always convert noise into a testable requirement before scoping. |
| 8 | First-principles problem decomposition — key steps? | 1) Strip the problem to its underlying business goal (ignore proposed solution). 2) Identify true constraints (data, infra, time, budget). 3) Rebuild the solution path from validated facts, not assumptions. Exam trap: accepting the client's proposed technical solution as the actual requirement. |
| 9 | Constraint vs Trade-off — how are they different? | Constraint = a hard limit that cannot be violated (e.g., no historical data exists). Trade-off = a choice between competing goods where you sacrifice one for another (e.g., speed vs accuracy). Exam scenarios often disguise a constraint as if it were a trade-off — check feasibility first. |
| 10 | Common FDE exam trap: solutioning before scoping | Proposing a specific technical solution (e.g., 'build an ML model') before discovery confirms the real bottleneck, data availability, and decision the output supports. Correct approach: structured discovery (IPO + MECE) before any build commitment. |
| 11 | Business-to-technical translation framework — 3 core questions to ask a client | 1) What decision or action will this output drive? 2) What data/inputs currently exist to support it? 3) What does success look like in measurable terms? These convert vague business asks into scoped technical requirements. |
| 12 | Feasibility analysis quick check — what to verify before agreeing to a client's stated solution | Verify: (1) required data/infrastructure exists, (2) technical approach matches actual constraint, (3) timeline/budget align with true scope. If any fails, re-scope the deliverable — don't just reject or blindly execute the original ask. |

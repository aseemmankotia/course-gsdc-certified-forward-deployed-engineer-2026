## Chapter 6: Prompt Engineering and LLM Workflow Design — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Does temperature=0 guarantee fully deterministic LLM output? | No. It minimizes randomness by always favoring the most likely token, but hardware/batching effects can still cause slight variance run-to-run. Exam tip: pair with a fixed seed parameter (if the provider supports it) for closer reproducibility — never claim '100% deterministic.' |
| 2 | When should you NOT use Chain-of-Thought (CoT) prompting? | For simple factual lookups, classification, or extraction tasks — CoT adds latency and tokens without accuracy gain. Exam tip: reserve CoT for multi-step math/logic/reasoning tasks. |
| 3 | Self-consistency prompting — core mechanism? | Sample multiple CoT reasoning paths (usually with higher temperature) and take the majority-vote final answer. Exam tip: trades N× cost/latency for higher accuracy on reasoning-heavy tasks. |
| 4 | ReAct pattern — what two elements does it combine in a loop? | Reasoning (Thought) + Actions (tool/API calls), interleaved with Observations: Thought → Action → Observation → repeat. Exam tip: used for agentic, tool-using tasks, not plain text generation. |
| 5 | Reflection technique — purpose? | The model critiques and revises its own prior output in a follow-up pass to improve quality. Exam tip: costs an extra LLM call per revision cycle; used for self-correction workflows. |
| 6 | Typical valid ranges for temperature and top_p in most LLM APIs? | temperature: 0–2 (0 = near-deterministic, higher = more random); top_p: 0–1 (nucleus sampling threshold). Exam tip: use LOW temperature + high top_p for extraction/consistency tasks, higher temperature for creative/diverse generation. |
| 7 | JSON mode (response_format) — what does it actually guarantee? | Syntactically valid JSON only — NOT that it matches your specific schema/fields. Exam tip: still validate the response against your schema, or use function/tool calling for stricter structural guarantees. |
| 8 | LLM-as-judge evaluation — biggest risk? | Judge-model bias: self-preference bias, position bias (favoring first/last answer), and verbosity bias (favoring longer answers). Exam tip: mitigate with randomized answer order, multiple judges, or rubric-based scoring. |
| 9 | Human-in-the-loop (HITL) vs LLM-as-judge — main trade-off? | HITL = higher accuracy/trust but slower and costlier; LLM-as-judge = fast and cheap but less reliable. Exam tip: use HITL for high-stakes decisions, LLM-as-judge for high-volume automated screening. |
| 10 | Prompt chaining vs routing — key difference? | Chaining = sequential steps where one call's output feeds the next call's input. Routing = a classifier/router decides WHICH chain, prompt, or model handles a given request. Exam tip: routing is used for cost optimization (send simple queries to a cheaper model). |
| 11 | Fallback pattern in LLM workflows — typical trigger? | Primary model/call fails, times out, or returns invalid/malformed output → fallback to a secondary model or a stricter retry prompt. Exam tip: combine fallback with retries and exponential backoff for resilience. |
| 12 | Prompt caching — how does it reduce cost/latency? | Reuses cached prefix tokens (e.g., static system prompt, few-shot examples) across repeated calls so those tokens aren't fully reprocessed/billed at full rate each time. Exam tip: place static content FIRST in the prompt to maximize cache hits. |
